## 0. Цель итерации

Прибор в режиме прибора:

1. одной кнопкой отвечает на вопрос «что с этой розеткой / этим сегментом»
   (AutoTest по образцу коммерческих тестеров, см. разведку, раздел 2);
2. даёт новые числа для *Zhodnocení*: метрики трафика и предел пассивного
   захвата, UDP-потери и jitter по размерам кадра, Path MTU, результаты
   AutoTest на стенде и в реальной сети;
3. выгружает результаты на флешку в форматах, которые открываются на ПК
   (PCAP, CSV, JSON).

Функции, которым нужно другое железо (кабельный тест, PoE, 10G, анализ
эфира, RTC), в итерацию не входят: разведка, раздел 6.

## 1. Общие правила для всех пунктов

### 1.1 Архитектура (из `CLAUDE.md`, решения от 03.08.2026)

- **R1. Одна функция, которой нужен netns, = один скрипт** в
  `~/diploma_project/`. Скрипт самостоятельный CLI-инструмент (работает по
  SSH без GUI), вызывается как
  `sudo ip netns exec <ns> python3 <script>.py <iface> [опции]`. GUI не
  импортирует Scapy и сам в netns не ходит.
- **R2. Последняя строка stdout машиночитаемая.** Существующие `TARGET4` и
  `TARGET6` не трогаем. Для новых скриптов предлагается единый вид
  `RESULT <имя_скрипта> <JSON в одну строку>` (решение пользователя, раздел
  4). Коды выхода: 0 тест выполнен (даже если результат плохой), 1 ошибка
  аргументов или запуска, 2 нет интерфейса или линка.
- **R3. Тонкий GUI.** Запускает скрипт в рабочем потоке, построчно пишет
  вывод в лог, разбирает последнюю строку регуляркой/`json.loads`, трогает
  виджеты только через `ui()`.
- **R4.** Параметры портов живут только в словаре `PORTS`.
- **R5.** Код только ASCII, без русских комментариев, комментариев минимум.
  После каждой правки `LC_ALL=C grep -P '[^\x00-\x7F]'`. Концы строк LF.
- **R6.** Что должно пережить перезагрузку, пишется в `/home/muk0015/...`
  или `/var/log`, не в `/tmp` (tmpfs).
- **R7. Блокировка по порту, а не на весь прибор.** Сейчас один флаг
  `test_running` на весь GUI и проверяется без блокировки. Нужно: на каждом
  порту не больше одного активного теста; пассивные прослушки (сниффинг,
  L2-прослушка) могут идти одновременно с активным тестом на другом порту.
- **R8. STOP у каждого теста дольше 3 с.** Скрипт ловит SIGTERM и успевает
  напечатать `RESULT` с `"aborted": true`.
- **R9. Каждый результат сохраняется** в `~/results/<YYYYMMDD>/` файлом
  `<HHMMSS>_<скрипт>_<порт>.json` (содержимое строки `RESULT` + время ISO 8601
  с поясом + значение `timedatectl show -p NTPSynchronized` + md5 скрипта).
  Экспорт (П5) копирует отсюда.
- **R10.** Новый скрипт проверяется сначала на veth-стенде без кабелей (как
  `ra_audit.py` 03.08), потом на петле `eth1 ↔ eth2`.
- **R11.** Всё, что меняет поведение прибора (что стартует при загрузке, что
  прибор раздаёт или шлёт в сеть), сначала согласуется с пользователем.
- **R12. Прибор по умолчанию молчит в чужой сети.** Активные кадры (DHCP
  DISCOVER, RS, LLDP fast start, UDP-нагрузка) только по нажатию, никогда
  при загрузке или по событию линка. Продолжение решения от 26.09 про DHCP.

### 1.2 Интерфейс

Исходные данные: 800 × 480, номинальная диагональ 5", то есть около 187 ppi,
**~7,3 px на мм**. Панель резистивная, одно касание, по краям точность хуже.

- **U1. Размер кнопок.** Основные действия не меньше **80 × 80 px (~11 мм)**.
  Ориентир: WCAG 2.2 SC 2.5.5 требует 44 × 44 CSS px, это около 11,6 мм;
  норма написана для веба, для прибора берём как ориентир физического
  размера. Второстепенные элементы (переключатель порта, BACK) не меньше
  60 px по меньшей стороне (~8 мм). Текущие кнопки главного экрана по оценке
  из `height=2` и Arial 10 около 40-45 px в высоту: при новой навигации
  увеличить. Оценку проверить по скриншоту.
- **U2.** Между соседними нажимаемыми элементами не меньше 8 px; ничего
  нажимаемого ближе 15 px к краю экрана.
- **U3. Никаких жестов:** ни свайпа, ни долгого или двойного касания.
  Прокрутка списков только кнопками «вверх/вниз» или «стр. N/M».
- **U4. Ввод текста последним средством.** Порядок: выбор из списка
  (найденные цели, профили) → нумпад → `OnScreenKeyboard`.
- **U5. Итог теста** одной строкой сверху: `PASS / WARN / FAIL` + ключевое
  число, шрифт не меньше 14 pt. Цвет всегда дублируется словом.
- **U6. Строка состояния** на всех экранах, не выше 32 px: время, батарея,
  линк и скорость порта 1 и порта 2, DHCP вкл/выкл, Wi-Fi.
- **U7. Экран функции** всегда одинаковый: заголовок и BACK в одном и том же
  месте, выбор порта двумя большими кнопками MONITOR / SENDER, кнопки
  действия, строка итога, лог.
- **U8.** Тест дольше 3 с показывает ход (секунды или проценты) и кнопку STOP.
- **U9.** Шрифт лога не меньше 9 pt (как сейчас), подписей не меньше 12 pt.

#### П0.2 Постоянные имена портов и горячее подключение (бэклог 2) · 1 сессия

Как: файлы `.link` в `/etc/systemd/network/` (`[Match] MACAddress=`,
`[Link] Name=`), копии в `SourceCodes/system/`. **Имена не `eth1`/`eth2`**:
systemd.link(5) прямо предупреждает, что имя, которое может выдать и ядро
(пример в документации `eth0`), приводит к гонке udev с ядром. Предлагаю
`mon0` / `snd0` (решение пользователя, раздел 4: меняет `PORTS`, скрипты,
текст и скриншоты). `setup_network.sh` научить поднимать порт поодиночке,
горячее подключение через правило udev или юнит systemd по появлению
интерфейса.

Попутно: сводка приветственного экрана перестаёт звать `sudo ip -n ...`
раз в 3 с. Вариант: маленькая служба держит `ip -n <ns> monitor link` и
пишет `/run/analyzer/ports.json`, GUI читает файл без `sudo` (тот же приём,
что `/run/ups/status`).

КП:
1. 10 перезагрузок подряд с адаптерами: каждый MAC каждый раз получает одно
   и то же имя и оказывается в одном и том же netns. Проверяет скрипт,
   сравнивающий `ip -n <ns> -br link` с таблицей MAC → имя: 10 из 10.
2. Загрузка без адаптеров, затем оба воткнуты: через ≤ 15 с оба порта в
   своих netns с адресами, GUI показывает линк без перезагрузки и без
   нажатий.
3. Один адаптер выдернут и возвращён во время работы: порт вернулся за
   ≤ 15 с, второй порт не трогался (идущий на нём ping не прервался).
4. За 10 минут простоя на приветственном экране в `journalctl` 0 строк
   `sudo`, порождённых опросом сводки.
5. Время от старта ядра до GUI не выросло больше чем на 2 с против 26.09
   (~36 с).

### П1. Статистика трафика и экспорт захвата (P1, бэклог 1) · 2 сессии

Скрипт `sniff_stats.py <iface> [--bpf "<фильтр>"] [--pcap <путь>]
[--max-mb N] [--interval 1]`. Фильтр передаётся в libpcap, то есть
выполняется как BPF в ядре, а не в Python (теория 2.3; pcap-filter(7)).
Раз в интервал печатает строку метрик, в конце `RESULT`.

Метрики (названия по Wireshark Statistics: Protocol Hierarchy, Endpoints,
Conversations, Packet Lengths): пакетов/с, бит/с, средний размер пакета,
доли TCP / UDP / ICMP / ICMPv6 / ARP / прочее, IPv4 против IPv6, число
уникальных хостов, топ-5 отправителей по объёму, топ-5 портов с именем
сервиса через `socket.getservbyport()`.

**Известный дефект текущей реализации** (`packet_sniff_thread` в
`gui_app.py`): протокол определяется по словам в текстовом выводе
`tcpdump`, а строки TCP в выводе tcpdump, насколько я знаю, слова «TCP» не
содержат (печатается `Flags [...]`). Тогда счётчик TCP всегда 0. **Не
проверено на железе:** проверить до замены (ping + iperf3 TCP при включённом
LIVE STATS). Если подтвердится, это строка в *Odhalené vady*. Кроме того,
захват жёстко привязан к `analyzer_monitor`/`eth1`.

КП:
1. **Точность счёта.** Петля, iperf3 UDP 10 Мбит/с, 30 с, `-l 1000`. Число
   UDP-пакетов в статистике равно числу датаграмм из JSON iperf3 ±1 %.
2. **Раскладка протоколов.** Смешанный трафик (100 ping v4, 100 ping v6,
   iperf3 TCP 5 с): доли совпадают с подсчётом `tcpdump -r <pcap>` по
   фильтрам `tcp`, `udp`, `icmp`, `icmp6` ±1 %.
3. **PCAP.** Файл открывается в Wireshark, `capinfos` показывает то же число
   пакетов, что GUI. Лимит `--max-mb` соблюдается.
4. **CSV.** Файл интервалов (время, пак/с, бит/с, средний размер, доли) и
   файл топа открываются в LibreOffice/Excel без правок. Разделитель и
   десятичный знак фиксированы и описаны в шапке файла.
5. **Предел пассивного захвата на 3B+.** Скорость UDP поднимается шагом
   50 Мбит/с до потерь захвата > 1 % (сравнение с iperf3, как в КП 1).
   Найденное число записано в протокол замеров. GUI при этом не зависает,
   STOP срабатывает за ≤ 2 с. Это число идёт в *Zhodnocení* как ограничение
   прибора. На каждой ступени записываются загрузка CPU (`pidstat` или
   `sar`) и температура SoC (`vcgencmd measure_temp`) плюс `get_throttled`:
   так же, как в дипломной Birka 2018 (A1 в разведке), чтобы числа можно
   было сопоставить с его таблицами.
6. **BPF в ядре.** С фильтром `icmp6` на фоне iperf3 TCP загрузка CPU процесса
   ниже, чем без фильтра (`pidstat`), и в статистике только ICMPv6.
7. Сниффинг выбирается на любом из двух портов.

### П1.2 Экран TRAFFIC: живая картина и работа с пакетами (P1) · 2-3 сессии

Приоритет пользователя (27.09.2026): **интерфейс и взаимодействие с
пакетами проработать всерьёз.** Образец по набору панелей: Network Traffic
Analyzer (Y6THAY), разбор в `04_external_refs.md`: лента пакетов, топ
отправителей с полосой объёма, телеметрия, раскладка протоколов. Оттуда
берём **только идею экрана**, код не копируем, NIDS-эвристики не берём.

**Процесс: сначала макет, потом код.** Экран собирается на фиктивных
данных, снимается `scrot`, показывается пользователю; реализация только
после его «да». Так же для страницы деталей пакета и для фильтров.

Раскладка 800 × 480 (исходная, уточняется на макете):

- сверху строка состояния (U6), 32 px;
- слева колонка ~300 px: четыре числа крупно (пак/с, Мбит/с, средний
  размер, число хостов); полосы долей TCP / UDP / ICMP / ICMPv6 / ARP /
  прочее с процентом и счётчиком; топ-5 отправителей с полосой объёма;
- справа лента последних ~8 пакетов, по строке: время, `src -> dst`,
  протокол, длина, имя сервиса; моноширинный шрифт;
- снизу ряд кнопок по U1: `START/STOP`, `PAUSE`, `FILTER`, `SAVE PCAP`,
  `SAVE CSV`, `BACK`; выбор порта MONITOR/SENDER по U7.

Взаимодействие (всё пальцем, без клавиатуры):

- **Фильтры кнопками-пресетами**, каждый превращается в BPF-выражение и
  применяется в ядре перезапуском `sniff_stats.py`: ALL, TCP, UDP,
  ICMP+ICMPv6, ARP, DHCP/DHCPv6 (`udp port 67 or 68 or 546 or 547`),
  ND/RA (`icmp6` с типами 133-137), DNS. Действующий фильтр всегда виден
  текстом над лентой.
- **Касание строки топа** ставит фильтр «только этот хост».
- **PAUSE** замораживает ленту для чтения, счёт в фоне идёт дальше.
- **Касание строки ленты** открывает страницу деталей: разобранные слои
  (Ethernet; IPv4 или IPv6; TCP/UDP/ICMP/ICMPv6 с полями; для RA флаги M/O
  и префиксы тем же разбором, что в `ra_audit.py`), листание кнопками.

Обмен скрипт ↔ GUI (правила R1-R3 и производительность):

- скрипт печатает **одну JSON-строку за интервал** (метрики + последние k
  пакетов в кратком виде + подробный разбор только для этих k), а не строку
  на пакет: в Tk не должен идти поток по каждому пакету;
- GUI перерисовывает экран не чаще 2 раз в секунду, только изменившиеся
  виджеты;
- детали пакета берутся из последней полученной порции, повторного захвата
  нет.

КП:
1. Макет утверждён пользователем (скриншот в журнале сессий).
2. Под потоком iperf3 TCP на петле касание любой кнопки экрана даёт
   отклик ≤ 300 мс (замер по логу времени нажатия и перерисовки), GUI не
   зависает 10 минут подряд.
3. Каждый пресет фильтра на смешанном трафике (ping v4/v6, iperf3, RA от
   dnsmasq, ARP) показывает только свой трафик; проверка сравнением с
   `tcpdump -r` того же PCAP по тому же выражению.
4. Касание строки топа за ≤ 2 с переводит статистику на один хост.
5. Страница деталей для RA показывает тип 134, флаги M/O и префикс так же,
   как `ra_audit.py` на том же кадре.
6. Проверка U1/U2 из П0.3 проходит с 0 нарушений на всех страницах экрана.
7. Лента на экране совпадает с `tcpdump -n` по адресам, протоколу и длине
   для 20 подряд взятых пакетов.

### П1.3 Генератор пакетов (P1/P2) · 1 сессия

Требование научрука к практической части: *Realizace generátoru a
analyzátoru provozu*. Сейчас генератор только iperf3. Нужен генератор
отдельных пакетов, чтобы показать двухпортовую архитектуру наглядно:
**шлём с SENDER, считаем на MONITOR в соседнем namespace.**

Скрипт `pkt_gen.py <iface> --proto icmp|icmp6|udp|tcp-syn|arp|rs
--dst <адрес> --count N --rate <пак/с> --size <B>` на Scapy. Пресеты
кнопками на экране TRAFFIC или отдельной плиткой. Защита как в П4: на
адреса вне стенда только с подтверждением (R12, RFC 6815).

КП:
1. 1000 ICMPv6 echo со скоростью 100 пак/с с SENDER: MONITOR насчитал
   ровно 1000 ICMPv6 echo request (фильтр ND/RA не мешает).
2. `--size` отражается в среднем размере на MONITOR с точностью ±1 B
   (с учётом заголовков, пересчёт описан).
3. Найдена и записана максимальная устойчивая скорость генерации Scapy на
   3B+ (без потерь на приёме), рядом загрузка CPU. Это число для
   *Zhodnocení* и довод, почему для нагрузки используется iperf3.
4. `rs` шлёт Router Solicitation, и на MONITOR при включённом dnsmasq
   виден ответный RA на странице деталей.

### П2. AutoTest одной кнопкой (P1) · 2-3 сессии

Скрипт `autotest.py <iface> [--profile <имя>] [--lease]`. Профили:
`~/diploma_project/profiles/*.json` (цели, имя для DNS, TCP-порт, пороги).
Шаги, каждый с оценкой PASS / WARN / FAIL / SKIP и временем:

1. **Линк:** несущая, скорость, дуплекс, автосогласование (`ethtool`).
2. **DHCPv4:** DISCOVER (Scapy), 3 с ожидания, все OFFER'ы: сервер, адрес,
   маска, шлюз, DNS, аренда, время ответа. По умолчанию аренду не брать.
   **WARN, если ответили больше одного сервера** (RFC 2131; у LinkRunner 10G
   это «secondary offers»). С `--lease` полный обмен и адрес на интерфейс на
   время прогона, в конце RELEASE. Чем брать аренду в netns (Scapy DORA,
   `dhcpcd`, `udhcpc`), исполнитель решает по тому, что есть на малине.
3. **IPv6:** RS → RA (переиспользовать `ra_audit.py`), есть ли SLAAC-адрес; при
   M=1 проба DHCPv6 (П7).
4. **Шлюз:** 3 ping v4 и, если есть, v6: RTT и потери.
5. **DNS:** запрос A и AAAA к выданному серверу, время ответа.
6. **Цели профиля:** ping или TCP connect (порт из профиля), RTT.
7. (P3) публичный IP / HTTP(S) HEAD к адресу из профиля.

Если на этом порту включён собственный dnsmasq, шаг DHCP = SKIP с причиной:
прибор не должен найти сам себя. Экран: список шагов с цветом и словом,
общий итог сверху, время прогона.

КП:
1. Стенд: dnsmasq с DHCP и RA на порту А, AutoTest на порту Б. Линк, DHCP,
   RA/SLAAC, шлюз = PASS; адрес DHCP-сервера совпадает с адресом порта А;
   время ответа DHCP в мс; DNS PASS на имени, которое dnsmasq знает локально.
2. Второй dnsmasq в том же сегменте (veth-стенд): шаг DHCP = WARN «2 servers»
   с обоими адресами.
3. Без DHCP-сервера: DHCP = FAIL за ≤ 5 с, зависимые шаги SKIP с причиной,
   прогон не зависает.
4. Полный прогон на стенде ≤ 20 с.
5. Без `--lease` после прогона на интерфейсе нет новых IPv4-адресов, а в
   leases dnsmasq нет записи прибора; с `--lease` запись освобождена.
6. Один прогон в реальной сети (EB215 с разрешения, или дома) сохранён
   JSON'ом для текста.

### П3. Порт: линк и соседи L2

#### П3.1 Диагностика линка (P1) · 0,5 сессии

Скрипт `port_info.py <iface>`: `ethtool` (скорость, дуплекс, автосогласование,
свои объявленные режимы, **режимы, объявленные партнёром**, link detected),
`ethtool -i` (драйвер), выбранные счётчики `ethtool -S` и `ip -s link`
(ошибки, отброшенные) с дельтой от прошлого запуска. `ethtool` лежит в
`/usr/sbin`, нужен `sudo`.

КП:
1. На петле для обоих портов 1000 / Full / autoneg on.
2. `ethtool -s <партнёр> advertise 0x008` (только 100baseT/Full): за ≤ 5 с
   прибор показывает 100 / Full, а в режимах партнёра только 100baseT/Full.
   Возврат настроек → снова 1000.
3. Кабель выдернут: «no link» за ≤ 2 с, без исключений в логе.
4. Строка в *Zhodnocení*: объявленные режимы партнёра получены без LLDP, то
   же, что LinkIQ называет FLP.

#### П3.2 L2-прослушка: LLDP, CDP, STP, LACP, VLAN (P2) · 1 сессия

Скрипт `l2_listen.py <iface> [-t 35] [--fast-start]`. Пассивно: LLDP
(ethertype 0x88cc, `scapy.contrib.lldp`, IEEE 802.1AB-2016), CDP (SNAP,
`01:00:0c:cc:cc:cc`), STP BPDU (`01:80:c2:00:00:00`), LACP (slow protocols,
0x8809), теги 802.1Q во входящих кадрах. С `--fast-start` один свой
LLDP-кадр, чтобы коммутатор ответил сразу (приём из PiScout). Вывод: имя
системы, chassis ID, port ID и описание, VLAN, адрес управления, TTL, каким
протоколом получено.

КП:
1. Стенд: со второго порта отправляется LLDP-кадр (Scapy или `lldpd` в
   netns). За ≤ 35 с показаны chassis ID, port ID, system name, TTL и адрес
   управления, совпадающие с отправленными.
2. VLAN: на порту-отправителе VLAN-интерфейс с id 100 и ping через него.
   Слушатель показывает VLAN 100. **Если драйвер снимает тег до захвата**
   (VLAN offload), результат попытки выключить offload (`ethtool -k/-K`)
   записан как установленное ограничение; тогда КП 2 = «задокументировано».
3. Без `--fast-start` скрипт не отправил ни одного кадра (`tcpdump -Q out`
   на порту: 0 кадров от прибора).
4. EB215: получено LLDP или CDP от коммутатора лаборатории **или**
   задокументировано, что коммутатор их не шлёт (закрывает вопрос из
   решения 03.08).

#### П3.3 Мигание порта (P3) · 0,2 сессии

`port_blink.py <iface> [-n 5]`: линк down/up с периодом 1 с.
КП: на петле партнёр видит n переходов; после завершения линк поднят,
адреса и маршруты на месте.

### П4. Измерения: JSON, UDP, развёртка, сервер (P1) · 1 сессия

Скрипт `perf_test.py <iface> <target> --proto tcp|udp [-b ..] [-l ..]
[-t ..] [-R] [--sweep]`. Везде `iperf3 -J`, разбор JSON вместо регулярки по
тексту (сейчас `execute_iperf` ищет `Mbits/sec` в выводе).

Развёртка `--sweep`: размеры кадра Ethernet из RFC 2544 (64, 128, 256, 512,
1024, 1280, 1518 B; номер раздела RFC сверить при написании текста),
пересчитанные в полезную нагрузку UDP отдельно для v4 (кадр − 18 − 20 − 8) и
v6 (кадр − 18 − 40 − 8). Для каждого размера: Мбит/с, пак/с, потери %,
jitter.

Скрипт `perf_server.py <iface>`: `iperf3 -s` в netns порта, гасится по STOP
(кнопка SERVER на экране SPEED).

**RFC 6815:** методы RFC 2544 нельзя применять в рабочей сети. Если цель не
из адресов стенда (10.0.1/24, 10.0.2/24, fd00:1::/64, fd00:2::/64,
link-local), GUI показывает предупреждение и требует подтверждения, а
развёртку не запускает вовсе.

КП:
1. TCP v4 и v6 на петле дают те же числа, что до переделки (276 и 274 Мбит/с
   ±5 %), число берётся из JSON.
2. UDP 100 Мбит/с 30 с на петле: показаны потери и jitter, потери < 1 %.
3. UDP 400 Мбит/с (выше потолка 3B+): потери > 0, прибор показывает
   фактическую, а не заданную скорость.
4. Развёртка по 7 размерам для v4 и v6 даёт CSV-таблицу за ≤ 3 мин на семейство.
5. SERVER: ноутбук в сегменте проводит тест против прибора; после STOP
   процесса нет в `ip netns pids`.
6. Таблица развёртки v4/v6 сохранена в `_context/data/` и описана в
   протоколе замеров.
7. В каждом результате `perf_test.py` есть средняя загрузка CPU за прогон,
   температура SoC в начале и в конце и `get_throttled`. Прогон с
   придушиванием помечается и в таблицу для текста не идёт.

Для текста: jitter iperf3 соотнести с определением interarrival jitter в
RFC 3550 (разд. 6.4.1). Что iperf3 считает именно по этой формуле, в его
документации я не нашёл: проверить по исходникам перед тем, как писать это
в тексте.

### П5. Экспорт на флешку (P1, бэклог 3) · 1 сессия

Скрипт `export_usb.py [--session <дата>]`: находит USB-накопитель (`lsblk`,
TRAN=usb, раздел FAT32/exFAT), монтирует, копирует `~/results/<дата>/` в
`analyzer/<hostname>_<YYYYMMDD_HHMMSS>/`, пишет `summary.txt` (ASCII, по
строке на тест), `sync`, размонтирует. `pcmanfm` удалён обновлением 26.09,
автомонтирования в киоске нет: монтировать самим.

КП:
1. FAT32-флешка, 10 МБ результатов: экспорт ≤ 10 с; «можно извлечь»
   появляется только после успешного размонтирования.
2. Флешка вынута во время копирования: понятная ошибка, GUI жив, повторный
   экспорт на вставленную снова флешку проходит.
3. Флешки нет: сообщение, без исключения.
4. На ПК: PCAP открывается в Wireshark, CSV в Excel/LibreOffice, каждый JSON
   проходит `python -m json.tool`.
5. В каждом JSON есть время с поясом, `NTPSynchronized` и md5 скрипта.
6. Флешка на тех USB-портах, что остаются свободными рядом с двумя
   адаптерами, не сбивает имена портов (проверка после П0.2).

### П6. Путь: traceroute и Path MTU (P2) · 1 сессия

Скрипт `path_test.py <iface> <target> --mode trace|pmtu [-6]`.
Traceroute: `mtr --report --json`, `traceroute` или `tracepath`, что есть на
малине. PMTU: бинарный поиск с DF (`ping -M do -s N`, для v6
`ping -6 -M do`) плюс учёт ICMP «fragmentation needed» / «Packet Too Big»
(RFC 1191, RFC 8201).

Стенд: на прямой петле PMTU всегда равен MTU линка, поэтому для непустого
результата нужен маршрутизатор с меньшим MTU на пути. Сначала только veth:
`ns_a <-> veth <-> ns_router <-> veth (MTU 1400) <-> ns_b`; потом через
железо: `eth1 <-> провод <-> eth2` (eth2 временно маршрутизатор с
`ip_forward=1`) `<-> veth (MTU 1400) <-> ns_target`. Все временные netns
удаляются после теста.

КП:
1. Петля без маршрутизатора: 1500 для v4 и v6.
2. Стенд с MTU 1400: 1400 для v4 и v6, ≤ 15 с.
3. Маршрутизатор режет ICMP PTB/Frag needed (правило nft): скрипт пишет
   «PMTU black hole suspected», а не выдаёт неверное число.
4. Traceroute v4/v6 на стенде показывает хоп маршрутизатора.

### П7. DHCPv6 в IPv6-аудите (P2) · 1 сессия

`dhcp6_probe.py <iface>` (или ключ в `ra_audit.py`): Solicit на
`ff02::1:2`, сбор Advertise (DUID сервера, адреса/префиксы, DNS). Сверка с
флагами RA: M=1 без ответа DHCPv6 → WARN; сервер отвечает при M=0 → INFO.
Классификация чужого RA/DHCPv6 в сообщениях по RFC 6104 (ошибка
администратора, ошибка пользователя, атака), со ссылками на RFC 8415 и
RFC 4861 в тексте сообщения, как у `ra_audit.py`.

КП:
1. Стенд, dnsmasq с `dhcp-range` для v6 без `slaac`: Advertise получен,
   адрес из диапазона.
2. dnsmasq с `ra-only`: Advertise нет, M=0, сообщение «DHCPv6 не
   используется».
3. RA с M=1 без DHCPv6-сервера (кадр собран Scapy): WARN.
4. `ra_audit.py` и `neigh_scan.py` после правки дают прежний результат на
   прежнем стенде (регрессия).

### П8. Периодический тест и профили (P2) · 1 сессия

2. Питание снято посреди прогона: CSV читается, последняя строка целая.
3. Блокировка экрана тест не останавливает.

## 3. Вне итерации

Кабельный тест и TDR, PoE, 10G, анализ эфира Wi-Fi, RTC, подсветка по GPIO:
другое железо (разведка, раздел 6). 802.1X: нужны учётные данные чужой
сети. Веб-интерфейс и приложение для телефона: противоречат концепции
самостоятельного прибора и добавляют поверхность атаки.

## 4. Решения, нужные от пользователя

1. Часовой пояс малины → `Europe/Prague` (П0.1)?
2. Новые имена портов `mon0` / `snd0` (или свои) вместо `eth1` / `eth2`
   (П0.2). Меняет GUI, скрипты, текст и скриншоты; оставить `eth1`/`eth2`
   через `.link` можно, но это ровно тот случай, от которого предостерегает
   systemd.link(5).
3. Формат последней строки `RESULT <скрипт> <JSON>` для новых скриптов (R2).
4. AutoTest и L2-прослушка в сети EB215: AutoTest шлёт DHCP DISCOVER и RS,
   это видно администратору. Спросить Nevlud'а заранее.
5. Порядок. Предлагаю: П0.1 → П0.2 → П0.3 → П1 → П1.2 → П1.3 → П4 → П2 →
   П3.1 → П5 → П3.2 → П6 → П7 → П8 → П9 → П10 → П11. Отличие от порядка в
   handoff: имена портов и навигация раньше метрик, потому что метрикам
   нужен свой экран, а серии замеров без постоянных имён несравнимы.
   Экран трафика и генератор сразу за метриками: это приоритет
   пользователя (27.09) и прямое требование научрука к практике.
