# Протокол замеров итерации 2 софта

> Замеры по ТЗ `11_tz_soft.md`. Сырые данные в `_context/data/`, ход работы
> в `03_session_log.md`. Замер принимается при `get_throttled` без битов

## П1. Точность и предел пассивного захвата (`sniff_stats.py`), 27.09.2026

**Стенд.** Петля `snd0 ↔ mon0` одним патч-кордом, линк 1000/Full. Трафик
между портами только по link-local со scope (маршрута между netns нет ни по
v4, ни по v6, это свойство прибора). Захват на `mon0` в `analyzer_monitor`,
`tcpdump -U -w -` с буфером ядра 4 МБ, разбор в Python через `struct`.
На время захвата на `mon0` выключены GRO, GSO и TSO (иначе захват видит
склеенные сегменты до 64 КБ), после захвата состояние возвращается; это
проверено `ethtool -k` до и после каждого прогона. Питание: модуль UPS на
зарядке. Малина одновременно генерирует нагрузку (iperf3 клиент в
`analyzer_sender`) и принимает её (iperf3 сервер в `analyzer_monitor`).

**Методика сверки.** Эталон один и тот же для всех проверок: pcap, записанный
тем же процессом, и его независимый пересчёт `tcpdump -r <pcap> <фильтр>`,
`capinfos` и `tshark`. Для UDP дополнительно число датаграмм из JSON iperf3
(`end.sum.packets`, `lost_packets`). iperf3 в UDP-режиме добавляет два
служебных пакета (4-байтный обмен при установлении теста), поэтому ожидаемое
число захваченных UDP = отправлено − потеряно получателем + 2.

### КП1. Счёт UDP

iperf3 UDP 10 Мбит/с, 30 с, `-l 1000`: iperf3 отправил 37 501 датаграмму, потерь
0; `sniff_stats.py` насчитал 37 503 UDP (+2 служебных). Отклонение 0,005 %,
допуск ±1 %. Потерь в ядре 0.

### КП5. Предел пассивного захвата

Данные: `data/20260927_p1_capture_limit.csv`. `pps` в таблице это скорость
отправителя; «потери захвата» = (отправлено − потеряно получателем + 2 −
захвачено UDP) / (отправлено − потеряно + 2); `dropped` из итоговой строки
tcpdump («packets dropped by kernel»).

Серия A и B, датаграммы 1000 B (кадр 1062 B):

| Потоков | Задано, Мбит/с | Реально, пак/с | Потери захвата | CPU Python | CPU всего (4 ядра) | °C |
|---|---|---|---|---|---|---|
| 1 | 50 | 6 249 | 0 | 29,9 % | 19,8 % | 51,5 |
| 1 | 100 | 12 499 | 0 | 63,4 % | 40,9 % | 53,7 |
| 1 | 125 | 15 624 | 0 | 79,2 % | 43,1 % | 53,7 |
| 1 | 150-250 | ~18 080 | 0 | 86,5 % | 41 % | 54,8 |
| 3 | 150-300 | ~18 500 | 0 | 89,3 % | 45 % | 54,8 |

При 1000 B генератор на самом приборе не выдаёт больше ~18,5 тыс. пак/с
(~150 Мбит/с) ни одним, ни тремя потоками. Причина выяснена в П1.3: на петле
каждый кадр дважды проходит единственную шину USB 2.0 малины (наружу через
`snd0`, обратно через `mon0`), и её практический потолок ~300 Мбит/с делится
пополам. Захват при этом не теряет ничего; iperf3-получатель на 3 потоках
теряет 9-12 тыс. датаграмм в сокете, а захват их видит.

Серия D, датаграммы 100 B (кадр 162 B), 3 потока:

| Реально, пак/с | Захвачено, пак/с | Потери захвата | CPU Python | °C |
|---|---|---|---|---|
| 15 000 | 15 000 | 0 | 58 % | 54,2 |
| 18 748 | 18 748 | 0 | 77,6 % | 53,7 |
| 22 498 | 22 498 | **0** | 96,5 % | 54,8 |
| 26 247 | 23 147 | **11,8 %** | 99,1 % | 53,7 |
| 29 996 | 21 544 | 28,2 % | 98,9 % | 53,7 |
| 33 746 | 21 252 | 37,0 % | 99,1 % | 54,8 |

**Результат: предел ≈ 22,5 тыс. пак/с без потерь, насыщение ≈ 23 тыс. пак/с.**
Узкое место одно ядро с разбором заголовков в Python (99 %), остальные ядра
свободны на 25-40 %. Для полноразмерных кадров 1514 B это ≈ 270 Мбит/с, то
есть около потолка USB 2.0 у 3B+ (300 Мбит/с по Product Brief): крупные
кадры захват успевает, мелкие нет. Предел выражается в пакетах в секунду, а
не в мегабитах.

Прогон C (37 500 пак/с по 100 B, захвачено 20 100 пак/с, потери 46 %) после
себя оставил `get_throttled = 0x80000`: бит 19, был достигнут мягкий
температурный лимит 60 °C. Прогон помечен и в таблицу не вошёл; серия D
снята после него, при каждой ступени биты текущего ограничения 0-3 нулевые,
температура 48-55 °C. Бит 19 липкий до перезагрузки.

Ограничения замера: нагрузку создаёт та же малина (iperf3 клиент и сервер
занимают 25-40 % CPU), поэтому число консервативное; внешний генератор
(ноутбук) не использовался. TCP с выключенным на приёме GRO на 149 Мбит/с
(~16 тыс. пак/с вместе с ACK) дал 1,8 % потерь захвата: приём TCP без GRO сам
по себе дорог для CPU.

## П1.2 (уровень скрипта). Разбор пакета против tshark, 27.09.2026

**Зачем.** Страница деталей пакета показывает разбор `pktdecode.py`, а не
Wireshark. Чтобы доверять ей, каждое поле разбора сверено с `tshark` 4.4.18
(тот же движок разбора, что у Wireshark) на одном и том же pcap.

**Набор.** 27 кадров Scapy со `snd0` на все ветки разбора (`_context/tests/
gen_test_frames.py`): ICMP echo, DNS запрос и ответ, DHCP DISCOVER и OFFER,
TCP SYN и SYN/ACK, IPv4 первый и не первый фрагмент, ARP запрос и ответ,
ICMPv6 echo, RS, два RA (M=1 prf High с MTU, префиксом и RDNSS; RA с
бесконечными временами жизни и префиксом /48), NS, NA, MLDv2 за Hop-by-Hop,
DHCPv6 Solicit, TCP SYN по v6, Packet Too Big и Destination Unreachable с
вложенным пакетом, IPv6 Fragment, 802.1Q VLAN 100, LLDP. Плюс живой трафик за
то же время: RA двух dnsmasq, ответы ядра (RST, NA, echo reply, ARP),
ответ dnsmasq на DHCPv6 и RS от `ra_audit.py`. Итого 58 кадров, pcap
`data/20260927_decoder_check.pcap`.

**Сверка** (`_context/tests/validate_decoder.py`): из текста разбора
извлекаются значения, из `tshark -T fields` те же поля (сборка фрагментов в
tshark выключена, иначе он прячет заголовок первого фрагмента до сборки).
Скалярные поля по первому вхождению, опции ND по всем.

**Результат: 58 кадров, 781 поле, 0 расхождений** (`data/20260927_decoder_check.txt`).
Первый прогон нашёл 8 расхождений: одно указало на настоящую дыру в разборе
(у IPv6-фрагмента с ненулевым смещением данные разбирались бы как
UDP-заголовок; исправлено, проверено отдельно), остальные были ошибками
сверщика и единиц (смещение фрагмента tshark отдаёт в 8-байтовых единицах,
разбор печатает байты).

Не разбирается намеренно: вложенный пакет ICMP-ошибки (показываются только
его адреса и протокол), MAC отправителя в ARP-запросе (он есть в строке
Ethernet).

## П1.3. Генератор пакетов `pkt_gen.py`, 27.09.2026

**Устройство.** Кадры собирает Scapy заранее (до 4096 разных, у каждого свой
номер последовательности), отправляет сырой сокет `AF_PACKET` с темпом по
`perf_counter`; Scapy в цикле отправки нет. `--size` = длина кадра без FCS,
как `frame.len` в Wireshark: заголовки считаются от собранного кадра, остаток
добивается нулями. Цели вне стенда (10.0.1/24, 10.0.2/24, fd00:1::/64,
fd00:2::/64, fe80::/10, ff02::/16) без `--force` отклоняются (RFC 6815).
Подготовка (импорт Scapy и сборка 1000 кадров) на 3B+ занимает 3-6 с.

**Стенды.** Сначала veth (`_context/tests/test_pktgen_veth.sh`): 1000 ICMPv6
echo на 100 пак/с приняты все 1000, 300 UDP `--size 512` приняты все со средним
512 B, 3 RS из 3, цель 8.8.8.8 отклонена. Остановка захвата сигналом (как
кнопкой STOP) 0,14-0,98 с. Затем петля (`test_pktgen_loop.sh`).

| КП | Проверка | Результат |
|---|---|---|
| 1 | 1000 ICMPv6 echo request, 100 пак/с, `snd0 → mon0`, счёт на `mon0` фильтром `icmp6 and ip6[40] == 128` | 1000 из 1000, потерь захвата 0 |
| 2 | `--size 200` (ICMPv6), `--size 1000` (UDP v6), по 500 кадров | средний размер на MONITOR 200 и 1000 B, отклонение 0 |
| 3 | 100 000 UDP, приём по аппаратному счётчику `mon0` (`ip -s link`), без захвата | см. ниже |
| 4 | 1 RS со `snd0` при включённом dnsmasq | на `mon0` виден RS и ответный unicast RA; разбор: тип 134, M=1 O=1, prefix `fd00:1::/64` L=1 A=1, MTU 1500, RDNSS, как у `ra_audit.py` |

КП3, предельная скорость генератора (потерь на приёме 0 во всех случаях):

| Кадр | Задано | Отправлено, пак/с | Мбит/с | CPU генератора |
|---|---|---|---|---|
| 100 B | 20 000 пак/с | 19 999 | 16,0 | 52 % |
| 100 B | максимум | **83 764** | 67,0 | 97 % |
| 1514 B | максимум | 12 964 | **157,0** | 17 % |

Мелкими кадрами генератор упирается в CPU (одно ядро Python), крупными в
шину: 157 Мбит/с при 17 % CPU.

**Почему iperf3 и почему 150, а не 276.** Проверено сразу: iperf3 TCP на той
же петле 150 Мбит/с с включёнными TSO/GSO на `snd0` и 147 Мбит/с с
выключенными, то есть сегментация в адаптере тут ни при чём. Числа 276/274
Мбит/с в работе сняты 03.08 против внешнего ноутбука; на петле и 21.09 было
150-151 Мбит/с. Все USB-порты и встроенный Ethernet 3B+ сидят на одной шине
USB 2.0 (Product Brief), а на петле кадр проходит её дважды. Отсюда вывод для
текста: на петле потолок ≈ 150 Мбит/с задаёт шина, генератор пакетов по
скорости в пакетах в секунду обгоняет iperf3 вчетверо (84 тыс. против
18,5 тыс.), а iperf3 остаётся инструментом измерения пропускной способности,
потому что считает её сам по протоколу и совместим с любым сервером iperf3.
