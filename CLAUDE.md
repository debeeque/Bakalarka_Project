## Софт на устройстве

Каталог на малине: `~/diploma_project/` (пользователь `muk0015`)

| Файл | Что делает |
|---|---|
| `setup_network.sh` | bash: создаёт netns `analyzer_monitor` / `analyzer_sender`, перекидывает туда `eth1`/`eth2`, назначает IP |
| `gui_app.py` | Tkinter GUI «Portable Network Analyzer», 800×480, вся логика управления |
| `arp_scan.py` | ARP-скан через Scapy |
| `capture.pcap` | пример захвата |

**Ключевая идея архитектуры:** логическая изоляция двух тестовых портов через
**Linux Network Namespaces (netns)** — это главный технический вклад работы.

Адресация:
- `analyzer_monitor` → `eth1` → `10.0.1.10/24`, цель `10.0.1.20`
- `analyzer_sender` → `eth2` → `10.0.2.10/24`, цель `10.0.2.20`

Функционал GUI (что реально работает):
- пассивный сниффинг + счётчик трафика в реальном времени (TCP / UDP / ICMP, детект IPv6)
- ARP-скан
- измерение пропускной способности через **iperf3** (v4 и v6) — важно: `iperf3`, не `iperf`
- ping v4 / v6
- **Nmap**: LAN-скан и Wi-Fi-скан (добавлено позже, по своей инициативе)
- виртуальная экранная клавиатура + **нумпад** для ввода IP пальцем (без физической клавы)

## Нерешённое / слабые места

- ~~Автономность~~ — **закрыто 02.08.2026**, эксперимент дома, протокол в
  `_context/01_device_dumps.md`. Целевым ПК выступал Huawei. Оказалось, что
  ручной `dhclient` не нужен вообще: как только устройство раздаёт адреса,
  NetworkManager на цели сам создаёт профиль и берёт и IPv4, и IPv6. Старый
  симптом был следствием обстоятельств лаборатории, а не свойством системы.

  Подтвердилось и главное про IPv6. При стателфул `dhcp-range` dnsmasq снимал
  **два** флага, а не один: M-флаг гнал цель к DHCPv6-серверу, и вдобавок у
  префикса был снят A-флаг, запрещая автоконфигурацию. Лечится одним словом
  `slaac` в `dhcp-range` — уже внесено в `setup_network.sh`. После правки ядро
  цели само построило `fd00:1::2e0:4cff:fe68:216` с меткой `proto kernel_ra`,
  то есть без единого процесса в userspace; на контрольном sender-порту со
  снятым A-флагом такого адреса не появилось.

  **Формулировка для текста уточнена:** разница не в ручном труде, а в
  необходимости процесса на цели. По IPv4 без DHCP-клиента адреса не будет
  никогда, по IPv6 ядро выдаёт link-local сразу по поднятию линка и глобальный
  адрес из префикса при поднятом A-флаге. Так утверждение не рассыплется на
  защите.
- ~~Nmap на `10.0.1.20`~~ — **разгадано 02.08.2026**, это был баг в `gui_app.py`.
  Режим LAN жёстко запускал сканер в `analyzer_sender`, а `10.0.1.20` находится
  за `analyzer_monitor`; namespace изолированы намеренно, маршрута между ними
  нет, и Nmap честно отвечал `failed to determine route`. Из правильного netns
  скан отрабатывает. Исправлено методом `netns_for()` — выбор namespace по
  подсети цели, применён в Nmap, ping и iperf3.
- В `gui_app.py` адреса цели (`10.0.2.20` и т.п.) всё ещё зашиты жёстко.
  Появился способ уйти от констант: SLAAC-адрес цели строится по EUI-64 из её
  MAC, то есть вычислим, а соседей можно перечислить через `ping6 ff02::1`.
- Нет аккумулятора и корпуса.
- **PDF не влезает в лимит EDISON.** Мартовская сборка — 22,8 МБ при потолке
